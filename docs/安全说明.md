# 安全说明

本文说明 Twice1200 面对的威胁、现有手工方案的真实漏洞,以及本项目的应对措施。
面向"知道怎么写代码、但不熟悉网络安全"的开发者。

---

## 一、先看现状:手工方案有哪些真实漏洞

`114514/` 目录里的原始方案能跑,但存在几个**不是理论、而是可被直接利用**的问题。

### 漏洞 1:密码通过命令行传递,对本机所有进程公开

原始启动命令:

```
edge.exe -d "以太网 2" -c mygroup -k mysecretpassword -a 10.236.167.114 -l 1200s.top:7777
                                          ↑ 密码在命令行里
```

**Windows 允许任何进程查询其它进程的完整命令行。** 一行 PowerShell 就能读到:

```powershell
Get-CimInstance Win32_Process | Select-Object Name, CommandLine
```

这意味着:**你机器上运行的任何程序——包括你安装的每一个软件、以及任何恶意代码——
都能直接读到这个密码,不需要管理员权限。**

同理,`frpc.toml` 里的 `auth.token = "<明文 token>"` 是明文落盘,
任何能读到这个文件的进程也能拿到它。

### 漏洞 2:使用官方示例值当密码,等于没设密码

原始配置用的是:

| 项目 | 值 | 问题 |
|---|---|---|
| 组名 | `mygroup` | n2n 官方文档的示例值 |
| 密码 | `mysecretpassword` | n2n 官方示例文件里的默认值 |

n2n 的"组名 + 密码"就是加入网络的唯一凭据。**因为太多人直接照抄示例不改**,
这两个值实际上等同于公开信息。**任何人用同样的组名和密码就能加入你们的虚拟局域网。**

而 n2n 组的是**二层网络** —— 加入后不只是在"同一个聊天室",
而是相当于**插在同一根网线上**:对方的 ARP 请求、广播流量、未加密的服务都能看见。

### 漏洞 3:frp 未启用 TLS

原始 `frpc.toml` 里没有 `transport.tls.enable` 配置。
frpc 与 frps 之间的控制连接、以及转发的数据,默认是**明文**的。
中间任何一跳(比如你连的公共 Wi-Fi 的运营者)都能看到内容和 token。

### 漏洞 4:frp dashboard 暴露风险

原始 `frps.toml` 只有 `bindPort = 7000`,**没有配置 `webServer`** ——
这本身是好事(没开管理面板就少一个入口)。

但要注意:**服务器上实际运行的配置未必等于手上这份文件**。
如果某天开了 dashboard(默认端口 7500)且用了默认口令,
等于把服务端的控制权交出去 —— 攻击者能看到 token、能改转发规则。

**待确认项:** 通过云控制台核实服务器上是否真的没有开 dashboard。

### 漏洞 5:凭据分散在多处,难以轮换

密码出现在:`frpc.toml`、`run.txt`、`启动n2n.cmd`、`n2n-connect.ps1`、
`新文件1.txt`(手写教程)、以及若干人的聊天记录里。
**想换密码时,你不知道有多少个副本要改。**

## 二、威胁模型

设计防御之前先明确"防谁"。

### 在防御范围内

| 威胁 | 场景 |
|---|---|
| **同机的其它进程** | 恶意软件、来路不明的工具读取你的命令行或配置文件 |
| **同组的不速之客** | 别人用猜到的组名密码加入你的 n2n 网络 |
| **文件被拷贝** | 配置文件随备份、U 盘、云同步泄露到别的机器 |
| **网络中间人** | 公共网络里的窃听 |
| **日志泄露** | 调试日志、错误报告、截图里意外带出凭据 |
| **误操作** | 用户照着示例填了弱密码 |

### 不在防御范围内(明确不承诺)

| 不防 | 原因 |
|---|---|
| **已获得管理员权限的攻击者** | 管理员能读进程内存、能挂钩 API,任何用户态方案都挡不住 |
| **服务器被入侵** | 服务器安全由云厂商与运维负责,客户端管不了 |
| **n2n 同伴的恶意行为** | 二层网络里同伴能看见广播流量,这是协议本身的性质,只能靠"只加信得过的人" |
| **供应链攻击** | 第三方二进制的来源与完整性目前未经验证(见第四节) |
| **物理访问** | 能直接操作你机器的人,DPAPI 在"当前用户已登录"时同样会被解开 |

## 三、本项目的应对

### 3.1 密钥不落明文

**配置文件里只有引用,没有密钥。**

```json
{
  "n2n": {
    "key": { "handle": "n2n/key", "source": "Dpapi" }
  },
  "frp": {
    "authToken": { "handle": "frp/token", "source": "Dpapi" }
  }
}
```

真正的密文在 `%APPDATA%\Twice1200\secrets.dat`,用 **Windows DPAPI** 加密。

**DPAPI 提供什么:** 密钥材料由 Windows 绑定到"当前用户 + 当前机器"。
把 `secrets.dat` 拷到别的机器或别的账户,**解不开**。

**DPAPI 不提供什么:**

- 不防"当前用户已登录时的其它进程" —— 同一个用户身份下,恶意程序也能调用 DPAPI 解密
- **不能跨机器共享**。所以本项目选择"每人自己配置",而不是"配置好一个包发给所有人"
- 重装系统或更换用户配置文件后,旧密文失效,需要重新输入

### 3.2 消除命令行明文

**目标:密钥不以命令行参数形式出现。这一目标对 n2n 已实测达成。**

`edge.exe`(n2n v3.1.0)支持用环境变量传密钥:

```
 N2N_KEY           | encryption key (ASCII), not with '-k ...'
```

**实测对照(见 README「edge.exe 探针结论」一节):**

| 密钥来源 | edge 的日志 |
|---|---|
| 无密钥 | `using null cipher.` + `WARNING: encryption is disabled in edge` |
| **`N2N_KEY` 环境变量** | `using AES cipher.` —— 加密正常生效 |
| `-k` 命令行 | `WARNING: switching to AES as key was provided` + `using AES cipher.` |

环境变量路径比命令行路径**少打印一条警告**,说明它走的是不同的代码分支。

**为什么这是实质性的改进:**

| | 命令行参数(`-k`) | 环境变量(`N2N_KEY`) |
|---|---|---|
| 谁能读到 | **本机任何进程**,无需特殊权限 | 读取其它进程的环境块需要调试权限 |
| 泄露途径 | 进程管理器、日志、崩溃报告、监控软件 | 显著更少 |
| 实测 | `GetCommandLineW()` 明文返回 | 命令行里干净,变量可被子进程读取 |

**结论:`N2N_KEY` 是应该采用的路径,`-k` 是必须避免的路径。**

不过要诚实说明残余风险:**在同一个用户身份下,提权后的攻击者仍可能读取环境块。**
环境变量消除的是"零成本、任何进程都能读"的那一类泄露,不是全部。

| 组件 | 方式 | 状态 |
|---|---|---|
| n2n | **`N2N_KEY` 环境变量**(已实测有效) | ✅ 方案确定,待实现 |
| frp | 配置写入 `%LOCALAPPDATA%\Twice1200\run\` 下的临时文件,ACL 收紧到仅当前用户,进程启动后立即删除 | 待实现 |

**实现时必须注意的一点:** 环境变量要在**创建子进程的那一刻**设置,
启动后立即恢复原值。否则同一进程后续启动的其它程序也会继承到这个密钥 ——
那等于把泄露面从"一个进程"扩大到"整个进程树"。

### 3.3 日志与报告的脱敏

所有输出经过统一处理:

- **`Redaction.Fingerprint()`** —— 把密钥变成 8 位指纹。
  用途:让用户确认"两台机器上填的是同一个密码",而不泄露内容
- **`Redaction.Describe()`** —— 只输出长度,不输出内容
- **`ConfigurationValidator.DescribeWeakness()`** —— 判定结果里**不含**密钥原文。
  这一点有专门的测试用例守着(`弱密钥:判定结果不包含口令本身`)

体检报告里只出现配置路径与问题描述,永远不出现凭据。

### 3.4 主动拦截危险配置

`ConfigurationValidator` 把下列情况报为**错误**(而不是放行):

- 组名或密码命中 n2n 官方示例值
- 组名过短(< 6 字符)
- 虚拟 IP 不在配置的网段内
- frp 服务端地址带协议前缀
- 同一客户端内规则名重复
- 多条规则争用同一个服务端端口

报为**警告**的:

- 关闭 frp TLS
- 网卡名含非 ASCII 字符但没有回退名称
- 未指定虚拟 IP(自动挑选有冲突风险)

**有一条元原则:校验器在读取配置时不接触密钥明文。**
判断密钥强度是另一个动作(`DescribeWeakness`),在用户输入时调用,
而不是在读文件时调用 —— 这样"读配置"这个高频操作永远不会把密钥带进内存里到处传。

### 3.5 开发期纪律

- **`.gitignore` 排除所有可能的密钥文件名**(`config.json`、`secrets.dat`、`*.toml`、`run.txt`、`*.log` …)
- **测试用例里不允许出现真实凭据**。测试用的是 `mysecretpassword` 这种公开示例值
- **不把用户的真实密钥写进日志、截图或反馈模板**

## 四、尚未解决的风险

**这一节是本文最重要的部分。** 以下是目前**没有解决**的问题,不要以为已经处理好了。

### 4.1 第三方二进制的来源未经验证(高)

`assets/` 下的二进制来自 `114514/` 目录,其来源与完整性**未经验证**:

| 风险 | 说明 |
|---|---|
| 可能被替换 | 无法确认它们与官方发布版本一致 |
| 可能被捆绑 | 未在干净环境中检查过是否有额外的网络行为 |
| 版本未知 | n2n 是 2022 年 2 月的 3.1.0;**TAP 驱动是 2020 年的 9.21.2** |
| **签名缺失** | 全部没有代码签名,无法验证发布者 |

**建议的处理顺序:**

1. 从官方渠道重新获取这些二进制
2. 核对官方公布的哈希值
3. 在隔离环境(虚拟机或沙箱)里观察实际网络行为
4. 把确认过的哈希写进 `assets/CHECKSUMS.txt`
5. 考虑自行编译 n2n(它是开源的),彻底消除"来路不明的二进制"

### 4.2 `edge.exe` 需要管理员权限才能看到 TAP 网卡(高)

**实测:`edge.exe` 在标准权限下启动即失败。**

```
[edge.c:1143] use manually set IP address
No Windows tap devices found, did you run tapinstall.exe?
```

而同一时刻,这台机器上 TAP 设备的注册信息是**完整**的:

```
设备实例  : ROOT\NET\0005
服务名    : tap0901
驱动文件  : C:\Windows\System32\drivers\tap0901.sys   9.21.2
匹配 ID   : tap0901
驱动 INF  : oem137.inf
.NET 可见 : 以太网 2 [TAP-Windows Adapter V9]  Down
```

**也就是说:驱动装了、设备注册了、.NET 能看见这块网卡,但 edge 说找不到。**

**已实测确认(同一命令、同一网卡,只差权限):**

| 条件 | 结果 |
|---|---|
| **提权** + 正确引号 | `Open device` → `created local tap device` → `edge started` ✅ |
| **非特权** + 正确引号 | `Cannot find tap device "以太网 2"` 立即退出 ❌ |

**结论:启动 `edge.exe` 必须提权。这是架构约束,不是实现细节。**

> 补充说明:探测过程中还发现了一个**独立的** bug ——
> `Start-Process -ArgumentList` 不会为含空格的参数自动加引号,
> 导致 `"-d 以太网 2"` 被拆成 `-d 以太网` 和 `2`。
> 这曾经让我们误以为"TAP 驱动坏了/网卡被禁用了"。详见 README「探针结论 3」。
> 它和权限问题是**两件独立的事**,各自都会单独导致连接失败。

**对安全设计的影响:**

1. **"启动 edge"必须被归类为需要提权的操作。** 提权辅助进程不是可选项。
2. 提权进程的生命周期因此变长:不只是"装一次驱动就退出",
   而是**每次连接都要以管理员身份启动 edge**。
   **这扩大了攻击面,必须谨慎处理:**
   - 辅助进程只接受来自本程序主进程的指令(命名管道 + ACL 限制到当前用户)
   - 不解析来自外部的输入
   - 用完即退,不常驻
   - **它读到的密钥只用于启动 edge,不做其它用途,不写日志**
3. 必须向用户解释"为什么每次连接都要弹 UAC" —— 否则会被当成设计缺陷。
   原手工方案让用户"以管理员身份打开 cmd"其实就是在做同一件事,
   只是没有说明原因。**这正是这个程序该补上的价值。**
4. 需要重新评估 3.2 节的结论:密钥走环境变量确实消除了 argv 泄露,
   但现在它要穿过一个**提权进程**。因此:
   - 环境变量在主进程侧设置,由提权辅助进程继承,而不是通过命令行传给辅助进程
   - 辅助进程用完立即从自身环境块中清除
   - 这条路径需要专门的测试,不能假定它安全

### 4.3 Windows Defender 会删除 `frps.exe`(中)

**实测复现:复制 `frps.exe` 后约 3 秒,文件被 Defender 实时防护删除。**

这是**灰名单误杀**(frp 被大量恶意软件滥用),不是文件真的有问题,但无法绕过。

对分发的影响:

- 客户端只需要 `frpc.exe`(不会被删),因此**主要功能不受影响**
- 若 `assets/` 里带 `frps.exe`,某些杀软可能删文件甚至隔离整个安装目录
- **用户必须被提前告知**,否则一定会来问"你的软件是不是有毒"

**当前处置:** 客户端资源不含 `frps.exe`,服务端部署时单独取用。

### 4.4 n2n 的二层网络属性(中)

n2n 组的是**二层**网络。加入同一组的成员之间:

- 能看见彼此的 ARP 请求与广播流量
- 能直接访问对方**未做认证**的局域网服务(共享文件夹、开发服务器、打印机……)
- 某些操作系统的默认共享配置可能暴露比预期更多的东西

**这不是缺陷,是"虚拟局域网"的定义本身。** 应对方式只有:

1. **只加信得过的人**
2. 把组名与密码设得足够强(组名相当于网络名,密码相当于入网口令)
3. 加入前检查本机的共享设置,关闭不需要的服务

**一个容易被忽略的点:如果你在接入 n2n 的同时连着公司网络或公共 Wi-Fi,
你的机器就在两个网络里同时存在。** 需要留意路由与共享策略。

### 4.5 虚拟 IP 冲突无法可靠检测(低)

程序通过 ping 扫描挑选空闲 IP,但:

- **开着防火墙的机器不响应 ping**,会被误判为"空闲"
- **当前离线的同伴扫不到**,等他一上线就冲突

IP 冲突的表现是"两台机器都时通时断",非常难排查。
**因此首次连接后必须人工确认没有冲突**,程序会在报告里明确提示这一点。

### 4.6 frp 服务端现状未核实(低,但需确认)

用户只有云厂商网页控制台,尚未核实:

- 实际运行的 `frps.toml` 内容(是否与手上那份一致)
- frps 的启动方式与自启配置
- **dashboard 是否开启并在公网暴露**
- 服务器上是否有其它服务共用端口

### 4.7 现有凭据未更换(已知,待处理)

那个 n2n 弱口令与 frp token **目前仍在有效使用中**。
按用户决定"先把程序做出来",暂未更换。

**但请记住:**

- 那个 frp token 已经存在于多个文件和聊天记录里
- 只要它还有效,任何知道它的人都能连上 frps
- **在把工具分发给别人之前,应当先轮换这些凭据**

### 4.8 本机 TAP 设备处于"半注册"疑似状态(待确认)

注册表里该 TAP 设备的 `Service` 与 `NetConnectionID` 值为空,
而通常这两个字段应当有值(`MatchingDeviceId = tap0901` 是有的)。

这可能是"驱动装了但设备实例不完整"的迹象,也可能只是 TAP-Windows 的实际存放方式不同 ——
**证据不足以定论,因此记录为疑似问题而不是结论。**

如果确实是半注册状态,现象会是:驱动看起来装了、设备管理器里能看到,
但 n2n 始终报 `No Windows tap devices found`,而重装驱动或重启能修好。
这类"看起来没问题但就是不工作"的状态是最难排查的一类,值得在实现里专门检测。

## 五、给用户的安全提示(分发时应当告知)

写进安装说明或首次运行向导:

1. **杀软会报警** —— 程序包内含 n2n 与 frp 的二进制,某些杀软会拦截或删除。
   这是灰名单误杀,不是病毒。需要把安装目录加入白名单。
2. **组名和密码就是门钥匙** —— 不要用示例值,不要发给不该给的人。
   拿到组名密码的人就能进入你们的虚拟局域网。
3. **接入期间本机在两层网络里** —— 注意共享设置,别把不该露的服务露出去。
4. **密钥存本机** —— 换电脑需要重新输入,这是设计如此,不是 bug。
5. **虚拟 IP 别撞车** —— 每台机器必须不同,首次连上后确认一下。
