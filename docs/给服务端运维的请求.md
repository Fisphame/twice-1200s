# 给服务端运维的请求

> 这份文档是**直接转发给服务器管理者**的。你不需要懂 n2n 或 frp,
> 照着下面的命令做、把输出发回来就行。

---

## 背景(一句话)

我在做一个小工具,把 n2n 组网和 frp 端口映射包成图形界面。
**客户端已经验证完全正常**(在本机起一个超级节点、连它、握手成功),
但连你服务器上的超级节点时**一直没有回包**。

所以问题在服务器的 supernode 那一侧。

---

## 我这边的实测结果(北京时间 2026-10-12 03:5x)

```
域名      1200s.top  →  www.1200s.top  →  39.105.139.45     ✅ 解析正常
TCP 7000  (frps 控制端口)                                   ✅ 可达
UDP 7777  (supernode)   发出探测包后 2 秒内无回包            ❌ 沉默
```

**关键点:同一台机器的 TCP 7000 是通的。** 说明服务器在线、网络可达,
问题局限在 **supernode 的 UDP 7777** 上。

另外,客户端连接时会打印:

```
WARNING: supernode not responding, now trying [1200s.top:7777]
```

## 需要你做的四件事

### 1. supernode 进程在跑吗?

```bash
# 方法一:直接看进程
ps aux | grep -i supernode

# 方法二:如果做成了服务
systemctl status supernode
```

**如果没有任何输出** —— 那就是原因,它没在运行。

### 2. UDP 7777 在监听吗?监听在哪个地址?

```bash
ss -ulnp | grep 7777
#   (老系统用:netstat -ulnp | grep 7777)
```

**两种结果的含义完全不同:**

| 看到的内容 | 含义 |
|---|---|
| `0.0.0.0:7777` 或 `*:7777` | ✅ 正常,监听所有网卡 |
| `127.0.0.1:7777` | ❌ **只监听本机回环,外面连不上** |
| 什么都没有 | ❌ 没在跑,或跑在别的端口 |

### 3. 云安全组放行 UDP 7777 了吗?

**这是最容易漏的一条,也是最可能的元凶。**

去云厂商网页控制台的「安全组 / 防火墙」里看:
需要一条**入方向**规则,允许 **UDP 7777**。

**常见误区:** "我 `-p 7777` 启动了就应该通" —— 不对。
云安全组是独立于服务器自身防火墙的一层,**不放行的话包在到达服务器之前就被丢了**。
表现出来正是"客户端一直等不到回包"。

顺便也看一下服务器自己的防火墙:

```bash
sudo ufw status              # Ubuntu / Debian
sudo firewall-cmd --list-all # CentOS / RHEL
```

### 4. 顺带确认:frp 的映射端口放行了吗?

TCP 7000(frps 控制连接)是通的,但 **frp 对外暴露的端口是另一个**。
比如映射了 25565,安全组里也需要放行 **TCP 25565**(如果映射 UDP 则放行 UDP)。

现在控制连接能建,但实际业务端口还没验证过 —— 很可能也没放行。

## 如果 supernode 没在跑:启动它

**我需要你用我这一份二进制。** 原因:我这边验证过它能与自己正常通信,
而 n2n 的版本差异会直接影响联邦/协议细节。

```bash
# 假设已经把 supernode 传到服务器上
chmod +x supernode

# 前台试跑一下,确认能起来
./supernode -p 7777 -v
```

**注意 `-v` 不是可选的美化参数** —— 实测确认 supernode 在没有任何参数时
只会打印帮助然后退出。

确认能起来后,挂成后台服务(否则你的终端一断它就没了):

```bash
nohup ./supernode -p 7777 -v >> /var/log/supernode.log 2>&1 &
```

**更好的做法是做成 systemd 服务**(能开机自启、崩溃自动重启):

```ini
# /etc/systemd/system/supernode.service
[Unit]
Description=n2n supernode
After=network.target

[Service]
Type=simple
ExecStart=/opt/n2n/supernode -p 7777 -v
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now supernode
sudo systemctl status supernode
```

## 另外两件安全上的事(需要你决定)

### ① 那个 frp token 需要更换

**目前用的 frp token 已经在多处文件和聊天记录里出现过**,而我刚把代码传到了一个
**公开的 GitHub 仓库**。虽然我在上传前把所有出现该 token 的地方都清掉了,
但这个值本身早就不是秘密了。

建议:

1. 在服务器 `frps` 配置里改一个新的 `auth.token`
2. 告诉我新值,我在客户端的界面里更新

### ② n2n 的组名和密码也建议更换

现在的组名只有 **2 个字符**。

n2n 组的是**二层**网络 —— 进去的人等于插在同一根网线上,
能看到彼此的 ARP 和广播流量,以及任何未加密的局域网服务。

组名 + 密码就是唯一的门钥匙。**2 个字符的组名配 9 位密码,被猜中的风险不低。**

建议换成 12 位以上的随机串。改完后告诉我,我同步更新客户端,
并通知其它组员一起改(**所有人必须用同一个值**,否则彼此发现不了)。

## 一个已知的"不是问题"的警告

启动时可能会看到:

```
WARNING: using default federation name; FOR TESTING ONLY,
usage of a custom federation name (-F) is highly recommended!
```

这个警告**与连不上无关**,只是建议。想消掉的话启动时加 `-F <自定义名字>`:

```bash
./supernode -p 7777 -v -F whatever-you-like
```

## 我要的最终结果

只要下面这一条能通过,就说明通了:

```
client → [supernode 39.105.139.45:7777] → 握手成功
```

我这边会跑验证,看到 `[OK] edge <<< ================ >>> supernode` 就成功。

**最可能的原因排序**(按我的判断):

1. **云安全组没放行 UDP 7777** —— 最常见
2. supernode 没在运行,或跑在别的端口
3. supernode 绑在了 `127.0.0.1` 而不是 `0.0.0.0`
4. 服务器自身防火墙拦了
